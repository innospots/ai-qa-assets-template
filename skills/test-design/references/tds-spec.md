# 测试设计编写规范

## 1. 定义与目标

测试设计说明书（Test Design Specification，简称 TDS）是测试设计阶段的标准输出物。它基于 PRD/PDD，回答「测什么、为什么测、覆盖到什么程度、风险在哪里」，**不**回答「具体怎么一步步测、每一步预期是什么」。

TDS 只写入 `designs/`，不绑定 Web、App、接口框架或某一个自动化工具。下游执行实现不在本规范中定义。

**本阶段禁止：**

- 编写逐步操作步骤与逐步预期结果
- 创建或修改 `cases/`、`flows/`、`modules/`
- 写入真实账号、密码、Token 或生产数据
- 把 TDS 写进 `docs/`

验收标准：

> 只阅读模块 Index 加一份场景 TDS，在不重新理解整份需求的情况下，应能明确该场景要验证什么、覆盖哪些测试点、以及可观察的业务结果。

---

## 2. 输入要求

`test:design` 开始前必须能定位以下输入；缺失且会影响范围或风险判断时，列入「待确认问题」，不得自行扩大业务范围。

执行顺序见 [`workflow.md`](workflow.md)：无完整文档时先 [`guided-intake.md`](guided-intake.md)（AskQuestion 引导）→ **`using-superpowers`** 拆任务 → 逐份生成与 [`review-checklist.md`](review-checklist.md) 审查。

| 输入类型 | 别名 | 必需 | 说明 |
| --- | --- | --- | --- |
| 产品需求文档（PRD） | 需求文档、需求说明 | 是 | 功能目标、用户故事、验收标准、业务规则、约束与非功能要求 |
| 产品设计文档（PDD） | **产品功能文档**、功能说明、交互说明 | 视情况 | 交互流程、状态机、异常与空态、平台差异 |
| 已有 TDS | `designs/` 存量 | 变更/对齐时 | 避免重复设计或覆盖已批准规则 |
| 接口/数据契约 | API 文档 | 视情况 | 字段约束、权限模型 |

**输入处理：**

- 用户提供的文件路径、附件或粘贴内容优先；在 Front Matter `sources` 中记录可追溯条目（文档名、章节或链接）。
- PRD 回答「做什么、验收是什么」；PDD/产品功能文档回答「怎么用、有哪些状态与异常」。两者互补，不互相替代。
- PRD 与 PDD/产品功能文档冲突时，停止扩大设计范围，在「需求溯源 / 待确认问题」中记录冲突并请求决策。
- 仅有 PRD 无 PDD 时：交互与异常细节标为待确认，不得臆造 UI 流程或错误文案。

## 3. 分层组织

不建议一个模块一份超大 TDS，也不建议按页面或控件拆文件。

```text
模块
  ↓
模块 Index
  ↓
场景功能（业务动作）
  ↓
场景 TDS
  ↓
测试场景 DS-
```

| 层级 | 文件 | 职责 |
| --- | --- | --- |
| 模块 Index | `designs/{domain}/index.md` | 模块共性、导航；不展开具体测试点 |
| 场景 TDS | `designs/{domain}/{scene}.design.md` | 一个可独立完成的业务动作要测什么 |

原则：**共性上收，差异下沉，规则只维护一份，场景独立可阅读。**

存量模块若仍使用 `README.md` 作为 Index，视为与 `index.md` 等价；**新建模块一律使用 `index.md`。**

## 4. 场景拆分

### 4.1 以业务动作为单位

推荐：`create-customer`、`update-customer`、`disable-customer`、`query-order`。

不推荐：`customer-list-page`、`customer-form-page`（页面是实现，不是测试对象）。

「创建客户」可同时覆盖列表、弹窗、接口、持久化、权限和审计，仍写在同一份场景 TDS 中。

### 4.2 拆分判断

同时满足以下三条，粒度通常合适：

1. **一个明确业务动作**（创建客户、绑定设备、用户登录）
2. **一个完整业务结果**（产生一条客户、建立绑定、获得登录态）
3. **能独立定义前置条件、规则、测试场景和可观察结果**

控件、字段校验、单个按钮不是独立 TDS，它们是所属业务动作的测试点。

出现多个互不相关的业务流程、用户目的或状态机时，继续按动作拆分；不要拆成 `create-customer-name-validation.md` 这类字段级文件。

目录最多三级：`领域 / 子模块 / 场景文档`。子模块各自维护 `index.md`。

## 5. 目录与命名

```text
designs/
├── README.md
├── customer/
│   ├── index.md
│   ├── create-customer.design.md
│   └── update-customer.design.md
└── merchant/
    ├── index.md
    ├── account/
    │   ├── index.md
    │   └── create-account.design.md
    └── recharge/
        ├── index.md
        └── recharge.design.md
```

- `{domain}`、`{scene}` 使用**小写英文 + kebab-case**。
- 场景文件必须带 `.design.md` 后缀，文件名与 `{scene}` 一致。
- 一个场景只维护一个 TDS；不按正向/反向、平台、优先级拆文件。

正确：`designs/auth/login.design.md`。错误：`designs/smoke/login-positive.design.md`、`创建客户.md`、`CreateCustomer.md`、`test-create-customer.md`。

业务数据名称与用途写在 TDS 中；具体值放 `data/`，二进制素材放 `fixtures/`，由 data 引用。Index 只说明数据位置，不维护大批固定值。

## 6. 编号体系

```text
需求条目
  ↓
模块 Index          {DOMAIN}-DESIGN
  ↓
场景 TDS            {DOMAIN}-{SCENE}-DESIGN     例：CUSTOMER-CREATE-DESIGN
  ↓
测试场景            DS-{DOMAIN}-{SCENE}-{NUMBER} 例：DS-CUSTOMER-CREATE-001
```

`{DOMAIN}`、`{SCENE}` 使用大写短横线，与目录名对应（`create-customer` → `CREATE`）。

| `DS-` 编号区间 | 类型 |
| --- | --- |
| `001-099` | 正向 / 正常 |
| `101-199` | 反向 / 校验与业务拒绝 |
| `201-299` | 边界 |
| `301-399` | 异常、恢复、专项故障 |

权限、幂等、状态、数据一致性场景并入上表最近的一类，不要另开编号段。已发布的 `DS-` 不因排序变化而重编号；测试意图根本变化时创建新 ID。

测试点过程编号 `TP-{DOMAIN}-{SCENE}-{NN}` **可选**。若测试点与 `DS-` 一一对应，省略 TP 表，以场景清单为唯一清单。

## 7. Front Matter

每份 Index 与场景 TDS **必须**使用 YAML Front Matter。禁止在其中保存账号、环境地址、执行工具名称或临时负责人。

### 7.1 模块 Index

```markdown
---
id: CUSTOMER-DESIGN
kind: index
name: 客户管理测试设计
module: customer
priority: P0
status: draft
version: 1.0
sources:
  - type: prd
    ref: docs/requirements/customer-prd.md
    version: v1.2
platform:
  - android
  - ios
tags:
  - customer
  - regression
---
```

### 7.2 场景 TDS

```markdown
---
id: CUSTOMER-CREATE-DESIGN
kind: scene
name: 创建客户测试设计
module: customer
scene: create-customer
priority: P0
status: draft
version: 1.0
inherits: CUSTOMER-DESIGN
sources:
  - type: prd
    ref: docs/requirements/customer-prd.md
    version: v1.2
  - type: pdd
    ref: docs/pdd/customer-create.md
    version: v1.0
platform:
  - android
  - ios
tags:
  - customer
  - smoke
  - regression
---
```

| 字段 | Index | 场景 | 格式 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | 必填 | 必填 | 见第 6 节 | 仓库内稳定标识 |
| `kind` | 必填 | 必填 | `index` / `scene` | 文档类型 |
| `name` | 必填 | 必填 | 中文 | 与一级标题一致 |
| `module` | 必填 | 必填 | 小写领域/模块目录名 | 与路径一致 |
| `scene` | 无 | 必填 | kebab-case | 与文件名（去 `.design.md`）一致 |
| `priority` | 必填 | 必填 | `P0` / `P1` / `P2` | 默认优先级 |
| `status` | 必填 | 必填 | `draft` / `review` / `approved` | 评审状态 |
| `version` | 必填 | 必填 | 语义化版本 | 随设计变更递增 |
| `inherits` | 无 | 必填 | 模块 Index 的 `id` | 声明继承公共规则 |
| `sources` | 必填 | 必填 | YAML 列表 | PRD/PDD 及版本 |
| `platform` | 必填 | 必填 | YAML 列表 | `android` / `ios` / `web` |
| `tags` | 必填 | 必填 | YAML 列表 | 领域与范围，不用目录表达 smoke |

新建默认 `status: draft`。评审通过后将 `status` 改为 `approved`。

## 8. Index 与场景的内容边界

| 内容 | Index | 场景 TDS |
| --- | --- | --- |
| 模块说明、模块范围 | ✓ | 不重复 |
| 公共角色与权限 | ✓ | 只补充特殊情况 |
| 公共字段规则、状态模型 | ✓ | 引用 |
| 公共前置条件、公共测试数据 | ✓ | 引用 |
| 公共测试要求 | ✓ | 引用 |
| 场景导航清单 | ✓ | — |
| 需求溯源（模块级缺口） | ✓ | 本场景条目 |
| 场景目标、特有前置、独有规则 | — | ✓ |
| 输入输出、主流程 | — | ✓ |
| 测试设计与 `DS-` 清单 | — | ✓ |
| 边界、异常、权限、幂等 | — | ✓ |
| 平台差异（场景相关） | 可摘要 | ✓ |
| 待确认问题 | 模块级 | 本场景 |

场景正文开头使用引用，不要复制 Index：

```markdown
> 本文档继承 [客户管理测试设计](../examples/customer-index.md) 中的公共角色、公共业务规则和公共测试要求。
```

## 9. 模块 Index 结构

```markdown
# 客户管理测试设计

## 1. 模块说明
## 2. 测试目标
## 3. 模块范围
## 4. 用户与角色
## 5. 公共前置条件
## 6. 公共业务规则
## 7. 数据与状态模型
## 8. 公共测试数据
## 9. 公共测试要求
## 10. 场景清单
## 11. 需求溯源
## 12. 待确认问题
## 13. 关联资料
```

Index **不要**展开逐步测试步骤或全部场景测试点。

### 9.1 模块说明 / 测试目标 / 范围

用简短语言说明模块做什么、整模块验证什么、包含与暂不包含哪些功能。不粘贴 PRD 全文。场景 TDS 不再完整复述模块范围。

### 9.2 用户与角色

公共角色与权限矩阵放 Index。场景仅补充特殊权限。

| 角色 | 查询 | 创建 | 修改 | 删除 | 启停 |
| --- | --- | --- | --- | --- | --- |
| 系统管理员 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 运营人员 | ✓ | ✓ | ✓ | - | ✓ |
| 查看人员 | ✓ | - | - | - | - |

### 9.3 公共前置条件与业务规则

只记录多场景共用前提（已登录、租户正常、服务可用）。场景特有条件（「必须已存在客户」）写到场景 TDS。

字段规则、唯一性、租户隔离等共享规则只在 Index 维护一份。

### 9.4 数据与状态模型

有明显状态时在 Index 给出状态与转换矩阵；场景 TDS 引用，不复制。无状态机可省略本节表格，改为说明关键数据对象。

### 9.5 公共测试数据与测试要求

只声明数据**名称、用途、所在 data/fixtures 路径**，不写真实值。

公共测试要求示例：业务操作除页面结果外，按场景验证 API、持久化、租户归属、业务状态、操作日志。各场景不必再抄一遍。

### 9.6 场景清单

这是 Index 的导航核心。

| 场景 | 文档 | 场景 ID | 优先级 | 状态 |
| --- | --- | --- | --- | --- |
| 创建客户 | [create-customer](../examples/customer-create-customer-tds.md) | CUSTOMER-CREATE | P0 | Ready |
| 修改客户 | `update-customer.design.md`（示意） | CUSTOMER-UPDATE | P0 | Ready |

`Ready` 对应场景 Front Matter `status: approved`；`Draft` / `Review` 与 `draft` / `review` 对齐。

### 9.7 需求溯源与待确认

模块级来源、缺口、冲突放 Index。状态：`open`、`resolved`、`deferred`。

## 10. 场景 TDS 结构

```markdown
# 创建客户测试设计

> 本文档继承 [模块测试设计](../examples/customer-index.md) 中的公共角色、公共业务规则和公共测试要求。

## 1. 场景说明
## 2. 场景目标
## 3. 前置条件
## 4. 输入与输出
## 5. 场景业务规则
## 6. 基本业务流程
## 7. 测试设计
### 7.1 正常场景
### 7.2 异常场景
### 7.3 边界场景
### 7.4 数据场景
### 7.5 权限场景
### 7.6 状态场景
### 7.7 重复操作与幂等
### 7.8 数据一致性
### 7.9 异常恢复
### 7.10 风险与优先级
### 7.11 平台差异
## 8. 测试数据要求
## 9. 测试场景清单
## 10. 假设与约束
## 11. 待确认问题
## 12. 关联资料
```

无状态变化可省略 7.6；无跨端差异可省略 7.11。不要为凑结构写空章节。

测试设计写**值得纳入场景清单的测试点**，不写点击路径、控件 ID、选择器或执行器命令。

### 10.1 场景说明与目标

说明谁在何种情况下执行什么操作，成功后的业务结果。控制在 1～3 段。

目标列出本场景必须验证的能力（合法可成功、非法被拒绝、唯一性、权限、幂等、持久化等）。

### 10.2 前置条件

推荐写法：「除模块公共前置条件外，需要：……」

### 10.3 输入与输出

| 类型 | 内容 |
| --- | --- |
| 输入 | 客户名称、客户编号、手机号 |
| 操作 | 提交创建客户 |
| 输出 | 创建成功或业务错误 |
| 数据变化 | 新增客户记录 |
| 后续影响 | 客户可被查询和使用 |

### 10.4 场景业务规则与主流程

只写本场景独有规则；公共字段规则引用 Index。

主流程只描述正常路径。异常放入第 7 节，不把流程图画成全部分支。

### 10.5 测试设计要点

**正常：** 全合法字段、仅必填、可选为空等。同构逻辑只保留一条主路径；模型、语种、附件等差异放入数据要求，禁止拆多条同构正向 `DS-`。

**异常：** 空值、重复、格式非法、请求错误。反向每核心功能大约 3–5 条。

**边界：** 必须写出具体值（1 / 100 / 101 字符），禁止只写「测试名称边界」。

**数据：** 按业务规则决定是否覆盖中英、空格、特殊字符等，不做无依据的全字段穷举。

**权限：** 同时考虑页面、接口与数据；不能只查按钮显隐。含跨租户/越权。

**状态：** 允许与不允许的转换；已删除等非法状态调用。

**幂等：** 连续提交、相同数据两次、超时后重试。检查是否重复处理、最终是否一致。

**一致性：** 列表、详情、API、持久化、租户、操作者、时间、日志。

**异常恢复：** 超时、中断、依赖失败。检查不产生残缺/重复数据，错误明确，可重试。故障注入默认标为专项/暂不自动化。

**风险：** 高影响项必须有对应 `DS-`；说明覆盖深度（冒烟 / 回归 / 专项）。

**平台：** 用表格标明 Android / iOS / Web 是否适用及差异。

### 10.6 测试数据要求

只定义需要什么**类型**的数据。

| 数据 | 要求 |
| --- | --- |
| 正常客户 | 所有字段合法 |
| 已存在客户 | 编号已占用 |
| 无权限用户 | 仅查看权限 |

敏感值声明由 env/CI Secret 提供，TDS 中不出现真实值。

### 10.7 测试场景清单

这是场景 TDS 的核心输出，描述测试意图，不是可执行步骤。覆盖矩阵并入本表，不再单开一章重复追溯。

| 场景 ID | 名称 | 类型 | 优先级 | 需求条目 | 意图 / 可观察结果 |
| --- | --- | --- | --- | --- | --- |
| DS-CUSTOMER-CREATE-001 | 合法完整信息创建客户 | 正向 | P0 | PRD 3.1 | 创建成功，列表与持久化可见 |
| DS-CUSTOMER-CREATE-101 | 客户编号重复 | 反向 | P0 | PRD 3.2 | 拒绝创建，不新增记录 |
| DS-CUSTOMER-CREATE-201 | 名称超过最大长度 | 边界 | P1 | PRD 3.3 | 校验失败 |
| DS-CUSTOMER-CREATE-301 | 服务异常时创建 | 异常 | P1 | — | 无残缺数据，可重试 |

清单字段也可以拆成每个 `DS-` 的小表（场景意图、前置状态、触发条件、可观察结果）。无论表格或小表，**禁止**出现逐步点击、选择器或逐步预期。

依赖未关闭的待确认问题时，在清单中标明该 `DS-` 暂缓，并在「待确认问题」中关联。

类型用语：`正向`、`反向`、`边界`、`异常`、`权限`、`幂等`、`状态`、`一致性`。与编号区间的对应见第 6 节。

### 10.8 假设、待确认、关联资料

假设必须最小且可审查。待确认用表：编号、问题、影响的 `DS-`、建议决策人、状态。关联资料链到 Index、PRD/PDD、data 路径，不链执行器脚本。

---

## 11. 写作边界

TDS 写测试意图与可观察现象，不写逐步操作。禁止出现：

- 逐步点击路径或逐步预期结果
- 控件 ID、选择器、坐标
- 执行器命令、脚本或某一自动化工具的 DSL
- 下游资产的字段模板、章节模板或编号规则

---

## 12. 修改与评审

- 业务要求变化时先更新 Index 或场景 TDS。
- 修改 Index 中的公共规则时，检查全部引用该 Index 的场景 TDS。
- 评审：分层是否合理、公共规则是否只维护一份、高风险是否有 `DS-`、意图有无歧义、PRD/PDD 是否可追溯、是否混入逐步操作或工具细节。
- 存量文档规范对齐由 `test:design` 执行，目标结构以 [`customer-index.md`](../examples/customer-index.md) 与 [`customer-create-customer-tds.md`](../examples/customer-create-customer-tds.md) 为准。

### 12.1 旧章节到新结构映射

存量场景 TDS（如 `designs/web/*.design.md`）调整时，按下列映射重排，**保留原 `DS-` 意图**：

| 旧章节 | 新位置 | 说明 |
| --- | --- | --- |
| 需求溯源 | Index §11；场景可留本场景条目 | 模块级缺口上收 |
| 业务理解与测试目标 | §1 场景说明 + §2 场景目标 | 不保留旧标题 |
| 测试范围 | 模块范围进 Index §3；场景不写完整模块范围 | Out of Scope 引用 Index |
| 功能分解与测试点、`TP-` | §7 测试设计；清单进 §9 | 与 `DS-` 一一对应则删 `TP-` 表 |
| 风险分析与优先级 | §7.10 风险与优先级 | 须有对应 `DS-` |
| 测试策略 | 并入 §7 各小节或删除 | 不单独成章 |
| 场景清单（`DS-` 表） | §9 测试场景清单 | 删「建议 TC」「建议 Case 类型」等列 |
| 数据与环境依赖 | §8 测试数据要求 | 只保留名称与用途 |
| 平台差异 | §7.11 平台差异 | 无差异可省略 |
| 覆盖矩阵 | 并入 §9，删除独立章节 | 避免与清单重复 |
| 假设与约束 | §10 假设与约束 | — |
| 待确认问题 | §11 待确认问题 | — |
| Case 生成指引 | **删除** | 不属于 TDS |
| 逐步操作 / 预期步骤 | **删除** | 不属于 TDS |

模块 Index 若仍为 `README.md`，对齐时改为 `index.md`，并将领域共用原则、场景导航写入 Index 标准章节（§1–§13）。

### 12.2 对齐时的禁止项

- 不因排版调整而修改已发布 `DS-` 的测试意图或编号。
- 不借对齐之机扩业务范围或新增未确认 `DS-`。
- 不把 Case、Flow、Maestro 内容写回 TDS。
- 不在多个场景重复粘贴 Index 已有公共规则。
